# 技術構成

## 1. 全体スタック

| レイヤー | 技術 | 理由 |
|---|---|---|
| デスクトップシェル | Tauri v2 | OS標準WebViewを使うためElectronより大幅に軽量。Rustバックエンドとネイティブに連携できる |
| フロントエンドUI | React + React Flow | ノードエディタの実装が速い。UIの磨き込み(簡易/上級モード切替、i18n)も web 技術の方が小回りが利く |
| 実行エンジン・自動化コア | Rust(cargo workspace) | UI Automation・Win32 APIへの直接アクセスが可能。軽量・高速・型安全で、機能追加時の影響範囲を crate 単位で閉じ込められる |
| UI操作 | `windows-rs` / `uiautomation-rs` | Microsoft公式バインディング。UI Automationのラッパークレートが実用レベルで存在する(2026年時点で保守されている) |
| 画像認識(完全一致・特徴点) | `opencv-rust` | テンプレートマッチング、ORB/AKAZE特徴点マッチングを実装 |
| 画像認識(軽量AI) | `ort`(ONNX Runtime) | 軽量embeddingモデルをONNX化して実行。GPU不要でCPUのみ動作 |
| スクリプトノード(JS) | `rquickjs`(QuickJS-NG) | ES2020対応、組み込み向けに設計されておりサンドボックス化しやすい。Boa(pure Rust実装)は代替候補だが2026年時点ではrquickjsの方が枯れている |
| 管理者権限起動 | Windowsマニフェスト埋め込み or 権限昇格用の別バイナリ + `runas` | Tauri本体はコミュニティのベストプラクティスとして「昇格が必要な処理だけ別プロセスに分離する」方式が推奨されている |

## 2. Workspace構成

```
desktop-flow-automation/
├── src/                    # React フロントエンド
│   ├── views/               # ノードグラフビュー / 直列リストビュー(将来) 等、複数ビュー
│   ├── modes/                # 簡易モード / 上級モードのUIバリアント
│   └── i18n/                  # en / ja 文字列リソース
├── src-tauri/                # Tauri本体(コマンド定義、権限設定)
├── crates/
│   ├── flow-schema/          # フロー定義のデータモデル・シリアライズ(serde)
│   ├── engine/                # フロー実行エンジン(ステップ実行、ブレークポイント、リトライ制御)
│   ├── automation/            # UI Automation / Win32 座標操作 / 座標系正規化(DPI・マルチモニタ)
│   ├── vision/                 # 画像認識(完全一致 → 特徴点 → AI のフォールバック制御)
│   ├── scripting/               # JSサンドボックス実行
│   └── secrets/                  # 資格情報管理(Windows Credential Manager連携)
└── Cargo.toml                     # workspace定義
```

`flow-schema` を中心に据え、GUI・実行エンジン・コードビュー・将来のAI生成のすべてが同じスキーマを参照する構成にする。

## 3. フローファイルの形式

**結論: 正規フォーマットはYAML。JSONを人間の編集対象にはしない。**

- JSONはコメント不可・末尾カンマ禁止など人間が手書きするには不向き。GUIで組んだフローを「コードで見る」際にJSONを見せると、当初懸念していた「コーディングできる人向けの窓口」として機能しない
- YAMLはコメントが書け、インデントベースで自動化フローの階層構造(ステップ→条件分岐→ステップ)と相性が良く、Git差分にも比較的強い
- 内部的にはRustの`serde`で`flow-schema`クレートの構造体に直接デシリアライズする。JSONへの変換層をあえて二重に持たない(変換処理が増えるほどバグの温床になるため)
- 将来的にYAMLで表現力不足を感じた場合のみ、専用DSLの検討に切り替える(P2)

### レイアウトとロジックの分離

ノードのx,y座標(レイアウト情報)をロジック定義と同一ファイルに混ぜると、ノードを少し動かしただけでGit差分が大きくなる。そのため:

```yaml
# flow.yaml (ロジック)
steps:
  - id: find_button
    type: vision.find_image
    params:
      target: assets/save_button.png
      mode: ai_similarity
      threshold: 0.85
```

```yaml
# flow.layout.yaml (レイアウト、機械的に再生成可能)
positions:
  find_button: { x: 460, y: 300 }
```

の2ファイルに分離する。

## 4. 座標系・DPI・マルチモニタの設計

- 記録する座標は常に「モニタID + そのモニタ内の相対座標(DPI非依存の論理ピクセル)」の組で保持する
- 実行時にモニタ構成(台数・解像度・配置)が記録時と異なる場合は、自動続行せず警告を出して一時停止する(誤操作防止を優先)
- DPI Awareness は Per-Monitor V2 を宣言し、Rust側で物理ピクセル⇄論理ピクセルの変換を一箇所(`automation`クレート)に集約する

## 5. 管理者権限への対応

- 本体アプリは通常権限で起動する
- 対象アプリが管理者権限で動いている場合にのみ、ユーザーの明示操作で「管理者として実行」するオプションを提供する(常時管理者権限では起動しない。最小権限の原則)
- 権限昇格が必要な操作は分離した実行バイナリに閉じ込め、`runas`経由で呼び出す

## 6. スクリプトノードのサンドボックス方針

- JSスクリプトノードは`rquickjs`で実行し、フロー変数の入出力だけを明示的にバインドする(グローバルなファイルシステム・ネットワークアクセスは既定で禁止)
- スクリプトノードを含むフローをインポート/共有する際は、実行前に警告を表示する
- Pythonサポートは権限分離の実装コストが高いため、MVPでは見送り、外部プロセス+制限付き実行(P2)として後日検討する

## 7. 簡易モード/上級モードの設計原則

- データモデル(YAML)は常に上級者相当のフル情報を保持する
- 簡易モードは「フル情報の一部だけを平易な言葉で編集し、残りはデフォルト値を使う」ビューのフィルタリングとして実装する。データが2系統に分岐しないことを最優先する
- ノード表示・配線表示のコンポーネントは`compact`/`detailed`のバリアントを持ち、モード設定で一括切り替える

## 8. UIデザイン

- フロントエンド実装時は `frontend-design` スキルを用い、テンプレート的なAI生成感(近黒+ネオン、クリーム+セリフ、Inter/Space Grotesk依存、絵文字装飾など)を避けた独自のビジュアルアイデンティティを維持する
- 初期モックアップ(Relayコンセプト)は `docs/design/` 配下に保管し、実装時の参照とする
