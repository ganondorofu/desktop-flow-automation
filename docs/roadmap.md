# ロードマップ

各フェーズは前フェーズの成果物の上に積む前提。フェーズ内の順序も上から着手する。

## Phase 0 — 基盤

技術的な土台を固める。ユーザーに見せる機能はまだ無くてよい。

1. Cargo workspace構成の作成(`flow-schema` / `engine` / `automation` / `vision` / `scripting` / `secrets`)
2. `flow-schema`: YAMLシリアライズ/デシリアライズできる最小のフロー定義構造体
3. `automation`: 座標クリック・キー入力(SendInput経由)の最小実装 + DPI正規化
4. Tauri + React の雛形起動、Rust側コマンドを1つ呼べることを確認

## Phase 1 — MVP(PADと同等ラインまで)

要件のP0を実装し、「単純な業務を自動化できる」状態にする。

1. UI要素選択(UI Automation)によるクリック/テキスト入力
2. 完全一致の画像認識・待機
3. 変数、If/Else分岐、ループ
4. ノードグラフGUI(React Flow)での組み立て・保存・読み込み(YAML)
5. ステップ実行・ブレークポイント
6. 実行ログ・エラー箇所の可視化
7. ノードごとのリトライ回数・間隔、失敗時挙動(即失敗/リトライ/スキップ)
8. マルチモニタ構成変更時の警告・一時停止
9. i18n基盤(en/ja)を最初から全文字列に適用

この時点でPAD代替として最低限使える状態になる。

## Phase 2 — 認識精度の差別化

このプロジェクトの核となる部分。

1. マルチスケールテンプレートマッチング
2. ORB/AKAZE特徴点マッチング
3. 完全一致→特徴点→AIの段階的フォールバック制御
4. 軽量AI類似検索(ONNXモデル、embeddingベース)
5. 認識パフォーマンスのプリセット(低/中/高)+ 詳細パラメータ(上級モードのみ)

## Phase 3 — 初心者/上級者の両立

1. 簡易モード用UIビュー(ノード表示のcompactバリアント、平易な文言での設定項目)
2. GUI⇄コード(YAML)ビューの相互切り替え
3. 簡易モード⇄上級モードの切り替えUI

## Phase 4 — 拡張機能

1. 秘密情報管理(Windows Credential Manager連携、マスキング表示)
2. JSスクリプトノード(rquickjsサンドボックス)
3. try/catch的なエラーハンドリングノード
4. フローファイルのレイアウト/ロジック分離保存

## Phase 5 — セキュリティ・配布

1. フローファイルのスキャン(危険操作・スクリプトノードの検知)
2. 外部フローインポート時の内容確認UI
3. 管理者権限起動オプション(権限分離バイナリ + runas)
4. インストーラ・自動更新

## 後回し(P2、Phase 5以降で検討)

- 自然言語からのフロー生成(バイブコーディング)
- 複数ビュー方式(直列リスト表示など)の追加
- Pythonスクリプトノード
- フロー共有・マーケットプレイス
- 関数ノード / 再利用可能なステップ列(2026-08-23 要望あり。方向性は下の未決事項を参照)

## 意思決定が必要な既知の未決事項

- スクリプトノードの入出力バインディングの具体的なAPI形状
- 簡易モードで隠すパラメータの範囲(どこまで隠すと「簡単」で、どこから「機能不足」になるか)は実際にユーザーテストしながら調整する
- ONNXで使う軽量モデルの選定(embeddingモデルの候補比較はPhase 2着手時に改めて調査する)
- 関数ノードの実装方式: (a) n8nの「Execute Workflow」のように別ファイルのフローをサブフローとして呼び出す方式、(b) よく使うステップ列をテンプレートとしてコピー貼り付けするだけの軽量な方式、のどちらにするか要相談
